# Matplan: middagsplanlegging, matpakker og Oda-sirkelen

Dato: 2026-07-18
Status: ferdig (kode), venter på produksjonsdata for nudge-fase

## Kontekst

Familien (to voksne, tre barn) står i en krevende periode, og mat er en daglig
energilekkasje: middager planlegges ofte kl. 14 samme dag og ender i lettvinte
løsninger eller 2–3 retter til kresne barn; fem daglige matpakker smøres i
praksis av én person og mye brødmat kastes («8 skiver i retur»); dagligvare-
handelen er flyttet til ukentlig Oda-bestilling for å spare penger og energi.

Målet: planlegge middager OG ferdigstille Oda-bestillingen i ÉN økt
(«onsdagsøkta»), senke matpakke-friksjonen, og lukke sirkelen med kvitterings-
parsing og forbrukssignal. Alt bor i mat-temaet (temasiden med food-dashboard).

## Faser

### Fase 0: Datamodell + rene domenemoduler
- `0038_matplan_middag.sql`: `shopping_lists` (strukturert ukehandleliste med
  `normalizedName` per vare), `meal_plans.updated_at`.
- `0039_matplan_matpakke_oda.sql`: `lunchbox_profiles/components/entries/returns`
  + `grocery_orders/grocery_order_lines`.
- Rene moduler i `src/lib/domains/food/`: `oda.ts` (søkelenker, klartekst,
  navnnormalisering), `meal-suggestions.ts` (deterministisk middagsscoring),
  `lunchbox.ts` (matpakkeforslag med rotasjon + retur-læring), `grocery.ts`
  (kategorisering, plan-vs-kjøp-matching). Alle med Vitest-tester.

### Fase 1: Toveis synk meal_plans ↔ ukeplan
- `src/lib/server/services/meal-plan-sync.ts`: retning A (plan → «middag: X»-
  punkt på dagens sjekkliste, med adopsjon av løse måltidspunkter) og retning B
  (dag-punkt → meal_plans). Kobling via `checklist_items.metadata.linkedMealPlanId`
  (IKKE i `PARSE_DERIVED_METADATA_KEYS` — overlever tekstredigering).
- Hooks i checklist-items POST/PATCH/DELETE, `/api/day-plan` og chat-verktøyenes
  tre `buildChecklistItemFields`-grener. REST + `manage_meal_plan` delegerer til
  `upsertMealPlan`/`deleteMealPlan`; duplisert `findOrCreateMealId` slettet.

### Fase 2: Oppskriftskartotek
- Ny «🍲 Oppskrifter»-tab på temaer med food-dashboard (`ThemeRecipesTab` +
  `RecipeSheet`). Hurtig-oppretting med bare navn. `GET /api/food/recipes`
  utvidet med `?q=`, `?tag=`, `?withStats=1`.

### Fase 3: Handleliste-tjeneste
- `shopping-list-service.ts`: `aggregateIngredients` (ren, flyttet fra
  generate-shopping-list-verktøyet), `mergeShoppingListItems` (bevarer
  avhukinger/manuelle varer ved regenerering), upsert mot `shopping_lists`.
- Endepunkter: `GET /api/food/shopping-list`, `POST …/generate`, `PATCH …/[id]`.
- `ShoppingListView` med Oda-søkelenke per vare + «Kopier handleliste».

### Fase 4: Onsdagsøkta + FoodDashboard-løft
- `MatplanSession` (fullskjerms fokusmodus, tre steg: middager → handleliste →
  til Oda) + `MealPickerSheet` (forslag/søk/fritekst/AI-fluktvei).
- `GET /api/food/week-session` (default neste uke) + `POST …/plan` (diff mot
  eksisterende dinner-planer; synken speiler til ukeplanen).
- `FoodDashboard` omskrevet til designsystemet; død chat-CTA koblet
  (`ThemeDataTab` sender `onOpenChat`/`onRefresh`).

### Fase 5: Matpakke-modul
- `lunchbox-service.ts` (barn = `persons` med `kind='child'`, auto-profiler),
  API under `/api/food/lunchbox/`, `LunchboxCard` (forslag per barn, «Pakk
  denne»/«Foreslå annet», tap-på-chip retur-logging), `LunchboxPrefsSheet`
  (preferanser + komponentbibliotek), AI-verktøy `manage_lunchbox`.

### Fase 6: Oda-kvitteringsparsing
- `email-processors/oda-receipt.ts` (gpt-4o-mini json): varelinjer med
  kategori, idempotens per gmailMessageId, kvittering erstatter
  ordrebekreftelse via unik (user, provider, order_ref), kobling til ukas
  handleliste. Nytt `processingType: 'oda_receipt'` i `/api/email/inbound`.
- Data-migrering oppretter «Oda-kvitteringer»-regel (`resonans/oda` +
  `*oda.com*`) — labelen polles allerede av Gmail Apps Script.

### Fase 7: Lager + plan-vs-kjøp
- `POST /api/food/grocery-orders/[id]/apply-pantry` («Legg i lager» — ett
  trykk, ikke automatikk; pant/gebyr/husholdning hoppes over) og
  `GET …/comparison` (kjøpt som planlagt / manglet / utenom lista).
- `GroceryReceiptCard` i FoodDashboard.

### Fase 8: Dagligvaresignal
- `economics_grocery_spend_weekly`: forbruk hittil i uka mot 4-ukers snitt
  (prorated ratio), via `queryCanonicalTransactions` med kategori
  `dagligvarer`. Kjøres av eksisterende `/api/cron/domain-signals`.

## Beslutninger

- **Onsdagsøkta er en dedikert fullskjerms-komponent, ikke en flow** — flow-
  stegtypene kan ikke uttrykke «7 dager × velg middag». `food_meal_chat`
  beholdes som AI-fluktvei.
- **Synk-loop umulig by construction**: `meal-plan-sync.ts` skriver direkte via
  db og kaller aldri HTTP/hverandre; hooks bor kun i API-/verktøylaget.
- **Regelbasert forslag først, ikke AI**: middagsscoring (favoritt-tag +2,
  <14d −3, 15–28d −1, «går snart ut»-match +1, rask +1) og matpakkerotasjon
  (likes +0.4, recency-straff 14d, returstraff 30d vektet alt/mesteparten/noe)
  er deterministiske og testbare. AI-inngang finnes via chat-verktøyene.
- **Handleliste = egen tabell** (`shopping_lists`), ikke checklist-items:
  strukturerte varer med normalisert navn trengs for Oda-lenker og
  kvitteringsmatching. Avhukinger/manuelle varer overlever regenerering.
- **Pantry-oppdatering er ett-trykks bekreftelse**, ikke helautomatisk.
- **Utsatt bevisst**: AI-genererte forslag, helautomatisk lagerføring,
  Google Chat dagligvare-nudge (trenger 3–4 uker kvitteringsdata),
  lagerpåminnelser, ukebudsjett-mål.

## Verifisering

- `npm test`: 1456 tester grønne (67 nye: oda, meal-suggestions, lunchbox,
  grocery, shopping-list-service, meal-plan-sync, prefiks-round-trip).
- `npm run check`: 0 feil.
- Kvittering E2E lokalt: POST Oda-epost-payload mot
  `/api/email/inbound?token=…` to ganger → én ordre (idempotens), «Legg i
  lager» og plan-vs-kjøp verifiseres mot temasiden.
- Synk E2E: `POST /api/food/meal-plans` → «middag: X» dukker opp i ukeplanen;
  redigering/sletting av punktet oppdaterer/sletter plan-raden.
